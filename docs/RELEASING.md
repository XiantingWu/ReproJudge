# Releasing ReproJudge

A release is cut from one exact standalone source identity that passes tests, scientific-shard validation, schema/public-surface checks, deterministic reference evidence, standalone export/package checks, release evidence validation, and final committed-evidence validation.

The commands below use `python3` on macOS/Linux. On Windows, use `py -3` instead. These command forms are portability guidance; the formal 0.3 release-authority platform is macOS ARM64 with CPython 3.11.x.

## 1. Standalone candidate gate

On the canonical standalone repository:

```bash
python3 -m pip install -e '.[dev]'
pytest -q
reprojudge doctor --strict --require-docker
python3 scripts/launch_surface_check.py
python3 scripts/validate_scientific_seed.py
python3 scripts/release_check.py
python3 scripts/release_source_check.py
python3 scripts/run_reference_suite.py --output .reprojudge/reference
python3 scripts/standalone_export.py --output /tmp/reprojudge-standalone
PYTHONPATH=/tmp/reprojudge-standalone/src \
  python3 /tmp/reprojudge-standalone/scripts/validate_scientific_seed.py
python3 -m build /tmp/reprojudge-standalone --outdir dist
python3 -m twine check dist/*
```

Install the exported-tree wheel in a fresh environment and verify `pip check`, `reprojudge --version`, `python3 -m reprojudge --version`, and `reprojudge doctor --strict`.

The scientific validator must report exactly 15 revision-pinned real-paper repository-discovery tasks and deterministic manifest/shard/task identities. Those cases define discovery benchmark content only; they are not complete reproduction results. Canonical repository URLs are release inputs: upstream repository renames or canonical owner/name casing changes require an explicit gold update and a complete fresh source/evidence cycle.

This repository intentionally contains **no GitHub Actions workflows**. All quality gates are runnable locally, and no automated CI, CodeQL, dependency-review, canonical-drift, or release-audit workflow is used.

## 2. Deferred external compatibility

Repo1/VeriRepro compatibility evidence is deferred to a future release. ReproJudge 0.3 does not vendor or claim any pinned external compatibility attestation: no external repository's recorded runs, task bytes, run IDs, or result hashes are part of the 0.3 source or its release evidence.

Reintroducing such an attestation requires explicit source-controlled evidence, an update of this release process, a change to the release-source fingerprint, and complete ReproJudge remeasurement. Public material must never present deferred compatibility work as current attestation.

## 3. Release evidence

Formal 0.3 evidence is generated by the release process on the exact candidate source:

```text
repository: XiantingWu/ReproJudge
runner environment: github-hosted
platform: macOS ARM64
evidence Python: 3.11.9
```

The release-authority measurement runs the complete local gate: full regression suite, `reprojudge doctor --strict`, launch-surface and scientific-shard validation, the deterministic four-case reference suite, candidate evidence generation, standalone export and package validation, and clean-install verification.

The evidence generation:

1. runs the complete regression suite and `reprojudge doctor --strict`;
2. validates launch surface and the exact 15-case scientific shard;
3. runs the deterministic four-case reference suite on the same source;
4. builds candidate release evidence with `scripts/build_release_evidence.py`;
5. temporarily copies that candidate to `benchmarks/release-evidence-0.3.0.json` and proves both evidence-required gates accept it;
6. removes the temporary promotion record from the checkout;
7. validates standalone export, exported scientific inputs, sdist/wheel/Twine and a clean installed wheel;
8. emits the exact candidate bytes plus SHA-256 digest for the promotion record.

Release-evidence schema v4 binds the measured repository/run/platform provenance; the `source_fingerprint` field must equal the measured tree.

## 4. Evidence promotion

From the successful measurement run, extract the candidate evidence payload and its SHA-256 digest, verify the digest matches, and commit those exact bytes as:

```text
benchmarks/release-evidence-0.3.0.json
```

Promoted evidence is intentionally excluded from the source fingerprint to avoid self-reference. Every other release-relevant byte — scientific tasks, tests, schemas, scripts, examples, and public documentation — remains source-bound.

The evidence promotion commit must change only the version-matched evidence file. If any covered byte changes, discard the candidate evidence and restart measurement.

## 5. Exact committed-evidence rerun

On the promoted exact head, both checks must pass before any tag is created:

```bash
python3 scripts/release_check.py --require-release-evidence
python3 scripts/release_source_check.py --require-release-evidence
```

The complete source/package gate must rerun on that exact head. The measured source fingerprint must still equal the promoted evidence fingerprint.

After the validated promotion is merged with a normal merge commit, **freeze `main`** from that point until the release event completes. If `main` advances, the release decision must be restarted at the new authority head.

## 6. Live public repository controls

The canonical repository is:

```text
XiantingWu/ReproJudge
```

Before any future release announcement, read back the following mutable control-plane state from GitHub under the maintainer control identity:

- verify repository description/topics/About links;
- enable private vulnerability reporting;
- protect `main` with appropriate review requirements;
- allow normal merge commits only for the evidence-preserving release path; disable squash/rebase merge for the protected launch branch policy;
- while visibility is public, test unauthenticated clone/install/demo/scientific-shard validation;
- confirm there is no private sibling-repository ancestry or internal-only file history in the repository.

Repository settings are control-plane state. Do not mark them complete from source code alone. This document states the required state; it is not proof of the current state.

## 7. PyPI publication

Before publishing `0.3.0`:

- confirm project ownership/availability for `reprojudge`;
- create `v0.3.0` only at the exact evidence-bound **current `main` commit**;
- create the GitHub Release from that exact tag;
- keep `main` frozen until publication completes successfully.

Publication is performed manually by the maintainer from the tested wheel/sdist built by the standalone gate (see section 1). Twine is used to upload the validated artifacts. No GitHub Actions publishing workflow exists in this repository, and no long-lived PyPI API token is stored as a repository secret.

After publication, download the actually published wheel and sdist, compute both SHA-256 digests, compare them with the tested manifest, then verify `pip check`, command/module versions, and `doctor --strict` in fresh environments. The release is not marked passed until the tested, published, and downloaded digests match for both artifacts.

## 8. Release dependency hash lock

The formal release authority platform installs the pinned toolchain with `--require-hashes` from:

```text
release-lock/requirements-cp311-macos-arm64.txt
```

### Lock identity and regeneration

- **Target environment**: macOS ARM64, CPython 3.11.x (currently 3.11.9), pip `26.2.1` (installed first).
- **Input**: `pyproject.toml` `[project.optional-dependencies].dev` (all entries are exact pins).
- **Generation command** (fresh venv, target platform):

  ```bash
  python3 -m venv /tmp/lockgen
  /tmp/lockgen/bin/python3 -m pip install 'pip==26.2.1'
  /tmp/lockgen/bin/python3 -m pip install --dry-run --ignore-installed --no-cache-dir \
    --report /tmp/lockgen/report.json -e '.[dev]'
  ```

  Then produce one `name==version --hash=sha256:...` line per resolved distribution (excluding the editable project itself) from `report.json` `download_info.archive_info.hashes`, sorted by normalized name. The macOS ARM64 wheel variants are the authority hashes.
- **Resolver/tool versions**: pip `26.2.1`; the report includes the full transitive graph as resolved on the target platform.
- **Validation command**:

  ```bash
  python3 scripts/verify_release_dependency_lock.py
  ```

  which re-resolves the graph and fails closed on version drift, hash mismatch, unlocked transitive dependencies, or missing locked entries.

### Review and update procedure

- Dependency pin changes in `pyproject.toml` are made by the maintainer with a reviewed, human-authored change;
- the maintainer must regenerate the lock from the target platform after every accepted dependency change, review the diff (version + hashes), and include it in the same hardening commit as the pin change;
- hash output is reviewed by comparing regenerated hashes against PyPI's published digests; the lock is committed only after `verify_release_dependency_lock.py` passes and the pinned install succeeds.

## 9. Release failure and rollback policy

Published artifacts are immutable:

- a published version is never re-published with different bytes;
- a published release tag is never moved or reused;
- partial PyPI publication (e.g. wheel uploaded but sdist failed) is **not** overwritten by retrying the same version; the partial state is assessed and a decision is made between finishing the same release at a new patch version or yanking the partial upload;
- a failed verification prior to publication (tag created but validation failed, or `main` advanced) requires a fresh exact-main validation; the tag is deleted only if it was never published and no release points at it;
- a critical defect found after publication is handled through a GitHub security advisory plus a patch (and yank if the artifact is unsafe); the same version number is never reused for the patch.

Decisions are recorded in the release notes and changelog. If in doubt, publish a new patch version rather than modifying an existing release.

## 10. GitHub automatic source archives and artifact provenance

GitHub Release auto-generated **Source code ZIP/TAR.GZ** archives are convenience artifacts, not the project's formal evidence-bound package authority. Formal authority is:

1. the validated **release source authority identity** (`source_tree_sha256`) of the exact `main` commit;
2. the wheel and sdist built from the fingerprint-checked standalone export and validated by Twine + clean-install gates;
3. the promoted formal release evidence (`benchmarks/release-evidence-0.3.0.json`).

Standard ecosystem attestations (e.g. SLSA/sigstore artifact attestation, SBOM) are **additive layers**, not replacements for ReproJudge semantic evidence; they are planned as post-0.3 enhancements and will be introduced only with their own verification gates. An SBOM is explicitly P2 / post-0.3.

## 11. Release non-claims

The release must never imply:

- 15 full paper reproductions;
- arbitrary-paper reproducibility;
- scientific correctness;
- that the deterministic reference suite measures scientific quality;
- that deferred external compatibility evidence is current 0.3 attestation;
- that release evidence constitutes independent third-party certification.
